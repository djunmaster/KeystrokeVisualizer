## Learnings

### What Worked

- **Optimistic UI Updates**: Implemented UI updates immediately before IPC call, providing instant feedback
  - Pattern: `setState(newValue)` → `await ipc.update()` → `setState(actualValue)`
  - Benefit: Better UX, users don't wait for IPC round-trip
  - Trade-off: Need error handling to revert on failure

- **Config Broadcast Mechanism**: Main Process broadcasts config changes via CONFIG_CHANGED channel
  - Works for: Settings window ↔ Overlay window ↔ Tray menu synchronization
  - All windows automatically update when any source modifies config

- **Mouse Pass-Through Toggle**: Dynamic control via IPC for drag handle interaction
  - Solution: `setMousePassThrough(false)` on hover → drag → `setMousePassThrough(true)` on release
  - Enables dragging while maintaining pass-through for key display

- **Position Save Strategy**: Save-only approach (no position modification)
  - Pattern: Electron native drag → `savePosition()` → read `window.getPosition()` → persist
  - Avoids window jumping to mouse coordinates

### What Failed

- **Initial Batch 4 Position Save**: Originally passed mouse coordinates to UPDATE_POSITION
  - Problem: Window jumped to mouse position on drag release
  - Fix: Changed UPDATE_POSITION to parameter-less, only reads window position
  - Learning: Electron's native drag (`-webkit-app-region: drag`) handles positioning, IPC only saves

- **Mouse Pass-Through Without Toggle**: Initially relied on `-webkit-app-region: drag` alone
  - Problem: Global `setIgnoreMouseEvents(true)` prevented drag handle interaction
  - Fix: Added SET_MOUSE_PASSTHROUGH IPC channel to dynamically toggle
  - Learning: Need explicit pass-through control when combining global ignore + local drag regions

### Key Decisions

1. **Use Optimistic Updates for Settings**
   - Alternatives: Wait for IPC response before updating UI
   - Reason: Better UX, instant feedback, settings changes are low-risk
   - Trade-off: Need rollback logic for errors

2. **Config Sync via Broadcast (not Polling)**
   - Alternatives: Poll config every N seconds, or no sync
   - Reason: Real-time updates, minimal overhead, consistent with IPC architecture
   - Implementation: Main Process sends CONFIG_CHANGED to all windows after any update

3. **Loading State for Settings Window**
   - Alternatives: Show empty form, show default config
   - Reason: Avoids flash of incorrect data, clear indication of async state
   - Implementation: `if (!config) return <Loading />`

4. **Error Handling Strategy**
   - Alternatives: Silent failure, toast notifications
   - Reason: Console error logging for dev, rollback prevents bad state
   - Future: Could add user-facing error notifications (Toast/Snackbar)
